02

Os quatro serviços

Cada serviço é dono exclusivo do seu banco — nenhum acesso cruzado direto, apenas via API síncrona ou evento assíncrono.

♔

Auth Service

AUTENTICAÇÃO & AUTORIZAÇÃO

Cadastro, login, emissão e validação de JWT (OAuth2). Demais serviços validam o token localmente, sem chamada síncrona a cada requisição.

RDS · Postgres
♞

Game Service

PARTIDAS & MATCHMAKING

Motor de partida, validação de lances, relógio e matchmaking. Comunicação com o cliente via WebSocket para latência mínima durante a partida.

ElastiCache · Redis DynamoDB · histórico
♛

Social Service

PERFIS, FEED & RELAÇÕES

Seguidores, feed de atividades, reações a partidas. Consome eventos de Game e Auth para manter o feed atualizado.

RDS · Postgres
♝

Analytics + LLM

DADOS & INFERÊNCIA

Processa o histórico de partidas (PGN), gera métricas de desempenho e alimenta um modelo de linguagem para insights e sugestões.

DynamoDB · leitura
03

SNS/SQS não serve para o lance em si — é assíncrono demais. O caminho crítico é outro:

Jogador AWebSocket
⇄

05

Observabilidade

Stack self-hosted em EC2, via docker-compose — controle total, sem vendor lock-in.

trace propagation: SNS/SQS não propaga contexto nativamente — traceId injetado manualmente em MessageAttributes na publicação e extraído no consumo.
06

Decisões conscientes

A favor

Menor complexidade operacional, custo previsível, stack 100% portável (LGTM), aprendizado transferível para qualquer cloud.

Atenção

EC2 de observabilidade é ponto único de falha — se cair, o time fica cego. Mitigado com Auto Scaling Group (min=1) + EBS persistente.

A favor

SNS/SQS elimina a operação de cluster Kafka — foco vai para a arquitetura dos microserviços, não para administração de infraestrutura de streaming.

Atenção

Sem replay nativo de eventos (diferente do Kafka) — se o Analytics/LLM precisar reprocessar histórico bruto no futuro, isso exige desenho extra.
